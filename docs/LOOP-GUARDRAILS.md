# Гардрейлс для системы петель (T5: Checkpointing & Hardening)

Правила, которые физически (не на честном слове) удерживают агентные петли от порчи проекта.

## Checkpointing — ветка на фичу, слияние только когда зелено

- Каждая новая фича/TDD-петля начинается с `git checkout -b <тип>/<название>` от `main`.
- Работа и коммиты идут на этой ветке.
- В `main` ветка сливается **только** после того, как все проверки (lint, typecheck, тесты) зелёные.
- Если петля объявила «фича готова», а на деле всё сломала — просто не сливаем ветку в `main` или откатываемся, не трогая рабочую историю.

Naming веток: `feat/<название>` для новой функциональности, `chore/<название>` для инфраструктуры/конфигурации, `fix/<название>` для багфиксов.

**Обновление**: репозиторий публичный ([github.com/Labien74/name-generator](https://github.com/Labien74/name-generator)), на `main` настроен GitHub Ruleset — слияние теперь возможно **только через Pull Request** с обязательным зелёным CI-чеком. Прямой `git push` в `main` физически отклоняется GitHub (`GH013: Repository rule violations`), причём правило действует даже для владельца репозитория (`current_user_can_bypass: never`). Локальный merge + push, которым мы пользовались раньше, больше не работает — см. обновлённый флоу внизу файла.

## Hardening — мягкие правила переведены в жёсткие через хуки

Раньше «не коммить сломанный код» было договорённостью (soft rule) — то, что я обещал делать сам перед каждым коммитом.

Теперь это жёсткое правило (hard rule), вшитое в git через [Husky](https://typicode.github.io/husky/) — [.husky/pre-commit](../.husky/pre-commit):

1. **Запрет прямых коммитов в `main`** — хук проверяет текущую ветку и блокирует коммит, если она `main`.
2. **Запрет коммита при красных проверках** — хук прогоняет `npm run lint`, `npx tsc --noEmit`, `npm test`; коммит невозможен, пока все три не пройдут.

Это работает независимо от того, кто коммитит — я (агент) или вы вручную. Хук хранится в репозитории (`.husky/`), а не в локальном `.git/hooks/`, поэтому переживает клонирование и синхронизацию — `npm install` сам его переустановит через `"prepare": "husky"` в `package.json`.

## Итог: как теперь идёт любая новая петля

```bash
git checkout -b feat/новая-фича
# ... red -> green -> refactor ...
git add .
git commit -m "..."           # локальный хук сам проверит lint/typecheck/тесты
git push -u origin feat/новая-фича
gh pr create --fill           # открыть Pull Request
gh pr checks --watch          # дождаться зелёного CI на GitHub
gh pr merge --squash --delete-branch   # слияние возможно только когда CI зелёный
git checkout main
git pull
```

`git merge` + `git push` напрямую в `main` теперь не сработает — GitHub Ruleset требует Pull Request с прошедшим статус-чеком `checks`.

## Loop and token budgets — жёсткий лимит на саму петлю

До этого момента лимит «10 итераций / 4 часа на фичу» был устной договорённостью между мной и агентом — ничего физически не мешало агенту продолжать после десятой итерации. Теперь это hard-стоп через **Claude Code PreToolUse-хук**: [.claude/hooks/loop-budget-guard.ps1](../.claude/hooks/loop-budget-guard.ps1), подключённый в [.claude/settings.json](../.claude/settings.json).

Как это работает:
- Состояние петли хранится в `.claude/loop-budget.json` (не в git — см. `.gitignore`), формат: `{ maxIterations, maxMinutes, iterations, startedAt }`.
- Любая команда `git checkout -b ...` (начало новой feature-ветки = начало новой петли) сбрасывает `iterations` в 0 и `startedAt` в текущее время.
- Любая команда `git commit` инкрементирует `iterations`. Если после инкремента `iterations > maxIterations` (по умолчанию 10) **или** с `startedAt` прошло больше `maxMinutes` (по умолчанию 240 = 4 часа) — хук возвращает `permissionDecision: "deny"` и коммит физически не выполняется, вне зависимости от того, считает ли агент себя обязанным остановиться.
- Любые другие команды хук пропускает без изменений.

Проверено вручную (пайп-тестом и через реальный вызов harness'а): нейтральная команда не создаёт файл состояния; `checkout -b` создаёт/сбрасывает его; `commit` инкрементирует; принудительно выставленные `iterations: 11` или устаревший `startedAt` (5 часов назад) блокируют следующий `commit` с понятным сообщением; следующий `checkout -b` после блокировки снова сбрасывает счётчик.
