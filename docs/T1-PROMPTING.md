# T1: Professional Prompting — промпт для этого проекта

Не ракетостроение, но и не тривиально: большинство людей сжимают сложную задачу в одно предложение и получают на выходе мусор. Разница не в «знании шаблона», а в понимании, какая информация ИИ обязательно нужна, прежде чем он начнёт работать. Рецепт — точная, упорядоченная последовательность из 4 частей.

## Формула

**Роль → Контекст → Задача → Формат результата**

## Разбор формулы для этого проекта

### Роль
Кто ИИ в этой работе. Для этого проекта: инженер, который пишет TypeScript/Next.js-код через строгий TDD-цикл (red → green → refactor) и работает внутри уже настроенной системы гардрейлов — не сам придумывает процесс каждый раз, а следует зафиксированному.

### Контекст
То, что ИИ обязан знать до начала работы, а не выяснять по ходу или додумывать:
- Спецификация проекта — [docs/PRD-name-generator.md](PRD-name-generator.md) (что уже решено: 3 сеттинга, P0/P1/P2, non-goals)
- Правила петли — [docs/LOOP-GUARDRAILS.md](LOOP-GUARDRAILS.md) (ветка на фичу, hard-gate через Husky, слияние только когда зелено)
- Текущая архитектура — `src/lib/names/` (движок `generateNames.ts`, датасеты по сеттингам, тесты в `__tests__/`), UI-экран `src/app/page.tsx`
- Технические особенности версии — `AGENTS.md` требует сверяться с `node_modules/next/dist/docs/` перед написанием кода (эта версия Next.js может отличаться от того, что ИИ «помнит» по обучению)

Без этого контекста ИИ либо переизобретёт то, что уже решено в спеке, либо нарушит уже настроенный процесс (например, закоммитит прямо в `main` — хотя это уже физически заблокировано хуком).

### Задача
Одна конкретная, проверяемая формулировка — не «сделай лучше», а что именно нужно сделать и по какому критерию понятно, что сделано.

### Формат результата
Как должен выглядеть ответ/результат, а не просто «код»:
- TDD-цикл: сначала тест (red), потом минимальная реализация (green), потом рефактор
- Ветка `feat/<название>` → коммит (хук сам проверит lint/typecheck/тесты) → слияние в `main`
- Короткий отчёт: что сделано, сколько итераций, что стоит проверить человеку

## Готовый шаблон (переиспользуемый)

```
Роль: [кто ты в этой задаче]

Контекст:
- Спека: docs/PRD-name-generator.md, раздел [...]
- Гардрейлы: docs/LOOP-GUARDRAILS.md
- Затрагиваемые файлы: [...]

Задача: [одна конкретная, проверяемая формулировка]

Формат результата:
- TDD-цикл (red → green → refactor)
- Ветка feat/<название>, коммит через хук, слияние в main
- Отчёт: что сделано / сколько итераций / что проверить
```

## Пример применения — следующая фича (P1: выбор периода для «Исторического»)

```
Роль: инженер, работающий по TDD-циклу в этом проекте.

Контекст:
- Спека: docs/PRD-name-generator.md, раздел Requirements → Nice-to-Have (P1):
  "Под-стили внутри категории: для «Исторического» — выбор конкретного
  под-периода/региона (Зап. Европа 1200–1600 / Вост. Европа 1200–1600 /
  США XX век / Европа XX век) или их микс"
- Движок уже поддерживает 4 периода внутри датасета: src/lib/names/datasets/historical.ts
- Текущий UI (src/app/page.tsx) периода не выбирает — берёт из всех 4 вперемешку
- Гардрейлы: docs/LOOP-GUARDRAILS.md

Задача: добавить в generateNames() и в UI возможность указать конкретный
период (или явный флаг "любой/микс" как сейчас по умолчанию) для сеттинга
"historical". Существующее поведение (без указания периода = микс всех 4)
не должно сломаться — на него уже есть тесты.

Формат результата:
- TDD-цикл (red → green → refactor)
- Ветка feat/historical-period-select, коммит через хук, слияние в main
- Отчёт: что сделано / сколько итераций / что проверить
```

Этим шаблоном можно закрывать любую следующую фичу проекта — не только P1 из этого примера.
